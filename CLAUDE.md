# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`cas-typescript-sdk` is a Node.js cryptography library that wraps the Rust [`cas-lib`](https://github.com/Cryptographic-API-Services/cas-lib) crate (pinned with an exact `=` version in `Cargo.toml`). The actual cryptographic implementations live in `cas-lib` (which itself builds on RustCrypto and Dalek-Cryptography). This repo contributes two thin layers on top of it:

1. A **Rust napi-rs FFI layer** (`src/`) that exposes `cas-lib` functions to Node as a native addon.
2. A **TypeScript wrapper layer** (`src-ts/`) that provides ergonomic, class-based, documented APIs over the raw FFI functions.

## Build & test commands

```bash
npm run build:rust   # napi build --release --platform -- --locked → produces native *.node + regenerates index.js / index.d.ts
npm run build:ts     # rimraf lib && tsc → compiles src-ts/ into lib/ (the published JS)
npm run build        # build:rust then build:ts

npm run rust:test    # cargo test --release --locked (runs the inline #[test] fns in src/)
npm run node:test    # npx playwright test (runs the TS tests in tests/)
npm test             # rust:test → build → node:test (the full CI pipeline)

npm run bench        # build:ts → bench:build → run the tinybench suite in benchmarks/ (needs build:rust first)
npm run bench -- --filter '*Hasher*' --job dry   # args after -- go to benchmarks/run.ts; --help lists them
```

- The TS tests import wrappers from `src-ts/`, but the wrappers `require` the native binding from the repo-root `index.js`. **You must run `npm run build:rust` before `npm run node:test`** or the native `.node` binding won't exist. `npm test` handles ordering for you.
- Tests use the **Playwright test runner** (`@playwright/test`) purely as a test framework — there is no browser/page usage despite `playwright.config.ts` defining chromium/firefox/webkit projects. Each test therefore runs three times (once per project). Run `npx playwright install` once before the first `node:test`.
- Run a single TS test file: `npx playwright test tests/symmetric.test.ts`. Filter by title: `npx playwright test -g "aes 128"`. Single project: `npx playwright test --project=chromium`.
- Run a single Rust test: `cargo test --release --locked aes128_encrypt_decrypt_test`.
- Benchmarks (`benchmarks/`, see its `README.md`) are TypeScript compiled by `benchmarks/tsconfig.json` to `benchmarks/dist/` (git-ignored). The suites import `"cas-typescript-sdk"`, which resolves through `package.json` `exports` to this package's own `lib/`, so they measure the published JS, not `src-ts/`. tinybench is ESM-only and the suite compiles to CommonJS, so it relies on `require(esm)` (Node 22.12+). `--job dry` runs each benchmark once; the runner exits non-zero if any benchmark or suite setup throws, and verify benchmarks throw on `false` (`expectTrue`).

## Dependencies & toolchain

- **`Cargo.lock` is committed** (this crate is a `cdylib` that ships binaries), so CI tests and npm releases compile the exact same crate graph.
- **Every build is `--locked`**: `rust:test`, `build:rust` (napi-rs forwards args after `--` to cargo) and the `napi build` steps in `main-publish.yml`. If `Cargo.toml` and `Cargo.lock` disagree, the build fails instead of re-resolving. Never add `cargo update` to a script or workflow.
- **Dependency bumps go through PRs**: change `Cargo.toml`, run `cargo update -p <crate>` (or a plain build without `--locked`) locally, and commit the resulting lockfile diff together with it so it can be reviewed. Bump `cas-lib` one release per PR with `cargo update -p cas-lib` only, and update the cas-lib version line in `README.md` in the same PR.
- **Dependabot** (`.github/dependabot.yml`, same policy as `cas-lib`) opens weekly PRs for cargo, npm and github-actions after a 7-day cooldown, titled `chore(deps): …`, `chore(deps-dev): …` and `ci(deps): …` so they pass the PR-title check. `cas-lib` is kept out of the grouped cargo patch updates, so every cas-lib release arrives as its own PR. Dependabot only reads the file from the default branch.
- **`rust-toolchain.toml` pins the compiler** (`1.100.0`, same as `cas-lib`); rustup installs it on first use, and it overrides any toolchain a workflow selects. It also lists every release target in `main-publish.yml`, so add a target there when adding one to the release matrix. Bump the channel in its own PR.

## Architecture & conventions

**The FFI boundary is code-generated, not hand-written.** `index.js` and `index.d.ts` at the repo root are auto-generated by NAPI-RS (`/* auto-generated by NAPI-RS */`) — never edit them by hand. They are regenerated by `npm run build:rust`. napi converts Rust `snake_case` function names to JS `camelCase` (e.g. Rust `aes128_encrypt` → JS `aes128Encrypt`).

**Data crosses the boundary as `Array<number>` (byte arrays).** Rust signatures use `Vec<u8>`; the TS side passes/receives `Array<number>`. Strings are used only where the underlying API is text-based (RSA PEM keys, password-hash strings). Convert text with `TextEncoder`/`TextDecoder` (see `tests/symmetric.test.ts`).

**The two source trees mirror each other by crypto domain.** Each domain has a Rust module under `src/` and a matching folder under `src-ts/`:

| Domain | Rust (`src/`) | TS (`src-ts/`) |
| --- | --- | --- |
| symmetric (AES, ChaCha20-Poly1305) | `symmetric/` | `symmetric/` |
| asymmetric (RSA, Ed25519) | `asymmetric/` | `asymmetric/`, `signature/` |
| hashers (SHA, BLAKE2) | `hashers/` | `hashers/` |
| password hashers (Argon2, bcrypt, scrypt) | `password_hashers/` | `password-hashers/` |
| key exchange (X25519) | `key_exchange/` | `key_exchange/` |
| message auth (HMAC) | `message/` | `message/` |
| sponges (Ascon AEAD) | `sponges/` | `sponges/` |
| hybrid (HPKE) | `hybrid/` | `hybrid/` |
| compression (zstd) | `compression/` | `compression/` |
| post-quantum (ML-KEM, ML-DSA, SLH-DSA) | `pqc/` | `pqc/` |

- Structs returned across the boundary (key pairs, encrypt/encapsulate results) are declared `#[napi(object, js_name = "<RustStructName>")]`, so they surface as plain JS objects / TS interfaces under their Rust name. Don't use `#[napi(constructor)]` for them: it generates a wrapped native class whose raw-pointer derefs CodeQL flags (`rust/access-invalid-pointer`).
- `src/lib.rs` declares every Rust module — a new module must be registered there.
- `src-ts/index.ts` is a barrel that `export *`s every domain's `index.ts` — a new wrapper must be re-exported up the chain to be part of the public API.
- Wrappers are plain classes that delegate 1:1 to the FFI function and carry the JSDoc (the FFI layer has none). Some domains add a factory + base-interface + enum to select an implementation at runtime — see `src-ts/hashers/` (`HasherFactory` / `IHasherBase` / `HasherType`) and `src-ts/password-hashers/` for the pattern to follow.

**Errors carry a stable `code`.** Every fallible `#[napi]` function returns `crate::Result<T>` (an alias for `napi::Result<T, ErrorCode>` in `src/lib.rs`) and passes its `cas-lib` result through `crate::map_cas_err`, which throws a JS `Error` whose `code` is a `CAS_*` string (one per `CasError` variant) and whose message is the variant's `Display` text. Don't return `napi::Result` from a new function: its errors only get napi's `GenericFailure` code. The alias must stay named `Result`, because napi-derive only treats a function as fallible when its return type's last path segment is `Result`. The TS side exposes the codes as the `CasErrorCode` enum plus `isCasError` (`src-ts/errors.ts`, exported from the package root). The `CAS_*` strings are public API, so never rename one. `ErrorCode`'s `match` over `CasError` has no `_` arm, so a `cas-lib` bump that adds a variant fails to compile until you add its code; then add the matching `CasErrorCode` member too, or the Rust test `every_code_is_in_the_typescript_enum` fails. Argument checks done in a wrapper throw a plain `Error` with no `code`.

**Adding a new algorithm** typically means: (1) write the `#[napi]` function in the right `src/<domain>/*.rs` module, returning `crate::Result<T>` if it can fail (and register the module in `src/lib.rs` if new); (2) run `npm run build:rust` to regenerate `index.d.ts`/`index.js`; (3) add a TS wrapper class in `src-ts/<domain>/` delegating to the new camelCase function; (4) export it through the domain `index.ts` and `src-ts/index.ts`; (5) add a usage example to `docs/EXAMPLES.md`; (6) add a benchmark to the matching suite in `benchmarks/suites/` (inputs built in the suite's `setup`).

## Keeping `docs/EXAMPLES.md` in sync

`docs/EXAMPLES.md` (linked from the README) is the public usage reference and must cover **every public method of every exported wrapper class**. Whenever you add, rename, remove, or change the signature of a public wrapper method in `src-ts/`, update `docs/EXAMPLES.md` in the same change — don't wait to be asked:

- Add new methods to the existing section for their domain, or add a new `##` section for a new domain, plus the class to the import block at the top.
- Examples import from `"cas-typescript-sdk"`, use the `toBytes`/`toText` helpers defined at the top of the file, and only use types that are actually exported from `src-ts/index.ts` (otherwise rely on inference).
- Mirror real argument order and semantics from the wrapper (e.g. hasher `verify*` takes the hash first, then the data).
- Check coverage with: `python -c "import re,glob;d=open('docs/EXAMPLES.md').read();print([(f,m) for f in glob.glob('src-ts/**/*.ts',recursive=True) if 'class ' in open(f).read() for m in re.findall(r'^\s*(?:public\s+|static\s+)*(\w+)\s*\(',open(f).read(),re.M) if m not in ('constructor','if','return','switch') and '.'+m+'(' not in d] or 'ALL COVERED')"`

**Memory zeroization is enabled globally.** `src/lib.rs` installs `zeroizing_alloc::ZeroAlloc` as the global allocator so freed heap memory is zeroed — relevant when handling key material.

## Inline Rust tests & NIST vectors

Rust modules keep their `#[test]` functions inline in the same `.rs` file (e.g. round-trip encrypt/decrypt checks). Some TS tests validate against official NIST CAVP known-answer vectors. SHA-2/SHA-3 ShortMsg and LongMsg files are committed under `tests/data/hashers/` (`tests/hasher.spec.ts`). AES-GCM, AES-KW/KWP and HMAC files are downloaded by `scripts/fetch-nist.mjs` (`npm run nist:fetch`, also run from `npm run node:test`) into git-ignored `tests/data/nist/`, each zip pinned by SHA-256; see `tests/aes-fips.spec.ts`, `tests/nist-aes-kw.spec.ts` and `tests/nist-hmac.spec.ts`. `tests/helpers/cavp.ts` parses the `.rsp` / `.txt` records. Which algorithms still have no NIST spec is tracked in #183.

The `tests/wycheproof-*.spec.ts` files use [Wycheproof](https://github.com/C2SP/wycheproof) vectors that are **downloaded, not committed**: `scripts/fetch-wycheproof.mjs` (run by `npm run node:test`, or `npm run wycheproof:fetch`) pulls the files listed in its `FILES` array from the latest upstream `main` (resolved to a commit SHA and logged) into `tests/data/wycheproof/` (git-ignored), so every run tests the newest vectors; files upstream has since removed (`PINNED_FILES`) come from a fixed commit. Downloads are HTTPS-only and each file must match the git blob SHA in upstream's tree, or the run fails. The script calls the GitHub API, so set `GITHUB_TOKEN` (or `GH_TOKEN`) if you hit its rate limit. Set `WYCHEPROOF_REF` to a SHA to reproduce a specific run. Load them with `loadWycheproof()` from `tests/helpers/wycheproof.ts`. Wycheproof `result` is three-way: assert `valid` and `invalid`, but let `acceptable` go either way.

## CI

`.github/workflows/main-pr-linux.yml`, `main-pr-macos.yml` and `main-pr-windows.yml` run `npm ci` then `npm test` on every PR, whatever its base branch (same as `cas-lib`), each across a Node.js LTS matrix (22.x, 24.x, 26.x) with `fail-fast: false`. `main-publish.yml` builds the native addon once on Node 26.13.1 (N-API binaries are not tied to a Node version) for each release target, then runs `npm run rust:test -- --target <target>` and `npm run node:test` against that freshly built `.node` (inside the container for the Docker targets) and uploads it only if both pass. It does this on every push to `main`, so `main` is always verified, but publishes only for a release (see Releases). The `x86_64-apple-darwin` job runs on an arm64 runner with an x86_64 Node (`node-arch: x64`) under Rosetta 2, because an arm64 Node can't load the x86_64 binary; if Node stops shipping `darwin-x64` builds, that target needs a new approach. When the supported Node.js lines change, update the three PR matrices, the Node version in `benchmarks.yml` (kept the same as the release builds'), the Node version in `main-publish.yml` (both `setup-node` steps, plus the `node-tarball` URL **and** its `node-sha256` for both Docker targets — the official `linux-x64` tarball from nodejs.org and the unofficial `linux-x64-musl` one, each hash taken from that release's `SHASUMS256.txt`) and the "Supported Node.js Versions" table in `README.md` together. Refresh the two `nodejs-rust` image digests in the same PR if the images need a newer Node or Rust (`docker buildx imagetools inspect ghcr.io/napi-rs/napi-rs/nodejs-rust:<tag>`, top-level Digest).

`benchmarks.yml` runs the tinybench suite on `ubuntu-latest` with Node 26.13.1: a `--job dry` smoke run on every PR (fails if any benchmark throws), a `--job short` run on push to `main`, and a manual run with a chosen filter, category and job. It writes `results.md` to the job summary and, except on PRs, uploads `results.json` and `results.md` as the `benchmark-results` artifact.

`audit.yml` (same policy as `cas-lib`'s) runs on every PR, on pushes to `main`, weekly and on demand. Its `cargo audit` job fails on any RustSec vulnerability in `Cargo.lock`, and on `unsound` or `yanked` warnings (`unmaintained` ones are only reported); its `npm audit` job runs `npm ci` then `npm audit --audit-level=high`, because the dev dependencies run in the release pipeline even though the package has no runtime ones. No advisories are ignored: an `--ignore` must be justified in its PR. An advisory is normally fixed by updating the lockfile (or bumping `cas-lib`), not by ignoring it.

Every workflow sets `permissions: {}` and grants each job only what it needs, checks out with `persist-credentials: false`, and pins actions to commit SHAs with a `# vX.Y.Z` comment (Dependabot keeps those current). Dependabot doesn't touch the `docker run` image digests, the Node tarball checksums or the `npm@` version in the publish job, so those are bumped by hand.

PR titles must follow [Conventional Commits](https://www.conventionalcommits.org/) (e.g. `fix(rsa): reject keys under 2048 bits`, or `feat!: ...` for a breaking change), because PRs are squash-merged and the title becomes the commit message and changelog line. `pr-title.yml` enforces this with the same regex as `cas-lib`, so keep the two in sync.

## Releases

Releases are made with [release-please](https://github.com/googleapis/release-please) (`release-type: node`; cas-lib uses release-plz, which only publishes Rust crates), and `CHANGELOG.md` uses cas-lib's format. The `release-please` job in `main-publish.yml` runs on every push to `main`:

1. It opens or updates a `chore: release <version>` PR that bumps `package.json` / `package-lock.json` and `.release-please-manifest.json`, and adds a `CHANGELOG.md` entry built from the Conventional Commit titles since the last release. Edit that PR to polish the entry; don't edit `CHANGELOG.md` entries anywhere else.
2. Merging it makes the job push the `v<version>` tag and create a GitHub Release whose body is that entry (job outputs `release_created` / `tag_name`).
3. Only then does the `publish` job run (`if: release_created`). It needs every build-and-test job, so a failing test on any target blocks the release. It runs in the `release` environment, which a repo admin must create in Settings → Environments with required reviewers (GitHub creates a missing environment on first use, but with no protection rules, so publishes would go out unreviewed). It is the only job with `id-token: write` (npm trusted publishing, with provenance). It fails if the tag isn't `v<package.json version>`, asserts that the tarball contains exactly the four release `.node` files (update that list when the build matrix changes), and skips `npm publish` if `npm view` finds the version already on npm, so a rerun never double-publishes.

`changelog-sections` in `release-please-config.json` maps commit types to cas-lib's groups: `feat` → Added, `changed` → Changed, `deprecated` → Deprecated, `fix` → Fixed, `security` → Security, `docs` → Documentation, everything else → Other; `!` commits are also listed under Breaking changes. release-please has no catch-all, so a type added to the `pr-title.yml` regex must be added there too or its commits are left out of the changelog. Set `release-as` in `release-please-config.json` only to force one specific version, and remove it in the PR after that release: while it is set, every release PR proposes that same version again. Never bump `package.json`'s version by hand; the release PR does it. release-please's own formatting needs a hand edit in each release PR: it lists breaking commits both under the breaking-changes heading and under their type, escapes `>` as `&gt;`, and links `(#N)` to `/issues/N`. `Cargo.toml`'s version is not kept in step: the crate is never published, and bumping it would also need `Cargo.lock` updated for `--locked` builds.

The PR that brings an epic branch into `main` must be merged with a **merge commit**, so each sub-PR's squashed Conventional Commit reaches `main` and gets its own changelog line. If it is squashed, put a release-please commit-override block listing every sub-PR title in the squash body; otherwise release-please sees one commit. The block's start marker is `BEGIN_` immediately followed by `COMMIT_OVERRIDE`, and its end marker is the same with `END_`. release-please reads the start marker from the body of the PR each commit came from and replaces the commit message with whatever follows it, so never write the literal marker in any other PR body (it would replace that PR's changelog line), including the epic PR's when it is merged with a merge commit (it would add duplicate lines). Write it split, as here, wherever you only need to mention it.

Epic workflow: each sub-issue is one PR into the epic branch (for example `epic/cas-lib-0.7`), squash-merged with a Conventional Commits title. Sub-PRs say `Part of #N`, because closing keywords only fire on PRs into the default branch; the epic → `main` PR lists the `Closes #…` lines. Keep the epic branch current by merging `main` into it, not rebasing, because other PRs are based on it.

A release PR opened with the default `GITHUB_TOKEN` doesn't trigger the PR workflows, so the job uses the `RELEASE_PLEASE_TOKEN` secret (GitHub App or fine-grained PAT with Contents and Pull requests read/write) when it is set.
