# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`cas-typescript-sdk` is a Node.js cryptography library that wraps the Rust [`cas-lib`](https://github.com/Cryptographic-API-Services/cas-lib) crate (pinned with an exact `=` version in `Cargo.toml`). The actual cryptographic implementations live in `cas-lib` (which itself builds on RustCrypto and Dalek-Cryptography). This repo contributes two thin layers on top of it:

1. A **Rust napi-rs FFI layer** (`src/`) that exposes `cas-lib` functions to Node as a native addon.
2. A **TypeScript wrapper layer** (`src-ts/`) that provides ergonomic, class-based, documented APIs over the raw FFI functions.

## Build & test commands

```bash
npm run build:rust   # napi build --release --platform -- --locked → produces native *.node + regenerates index.js / index.d.ts
npm run build:ts     # rimraf lib && tsc → compiles src-ts/ into lib/ (the published JS)
npm run build        # build:rust then build:ts

npm run rust:test    # cargo test --release --locked (runs the inline #[test] fns in src/)
npm run node:test    # npx playwright test (runs the TS tests in tests/)
npm test             # rust:test → build → node:test (the full CI pipeline)
```

- The TS tests import wrappers from `src-ts/`, but the wrappers `require` the native binding from the repo-root `index.js`. **You must run `npm run build:rust` before `npm run node:test`** or the native `.node` binding won't exist. `npm test` handles ordering for you.
- Tests use the **Playwright test runner** (`@playwright/test`) purely as a test framework — there is no browser/page usage despite `playwright.config.ts` defining chromium/firefox/webkit projects. Each test therefore runs three times (once per project). Run `npx playwright install` once before the first `node:test`.
- Run a single TS test file: `npx playwright test tests/symmetric.test.ts`. Filter by title: `npx playwright test -g "aes 128"`. Single project: `npx playwright test --project=chromium`.
- Run a single Rust test: `cargo test --release --locked aes128_encrypt_decrypt_test`.

## Dependencies & toolchain

- **`Cargo.lock` is committed** (this crate is a `cdylib` that ships binaries), so CI tests and npm releases compile the exact same crate graph.
- **Every build is `--locked`**: `rust:test`, `build:rust` (napi-rs forwards args after `--` to cargo) and the `napi build` steps in `main-publish.yml`. If `Cargo.toml` and `Cargo.lock` disagree, the build fails instead of re-resolving. Never add `cargo update` to a script or workflow.
- **Dependency bumps go through PRs** (Dependabot, #134): change `Cargo.toml`, run `cargo update -p <crate>` (or a plain build without `--locked`) locally, and commit the resulting lockfile diff together with it so it can be reviewed.
- **`rust-toolchain.toml` pins the compiler** (`1.100.0`, same as `cas-lib`); rustup installs it on first use, and it overrides any toolchain a workflow selects. It also lists every release target in `main-publish.yml`, so add a target there when adding one to the release matrix. Bump the channel in its own PR.

## Architecture & conventions

**The FFI boundary is code-generated, not hand-written.** `index.js` and `index.d.ts` at the repo root are auto-generated by NAPI-RS (`/* auto-generated by NAPI-RS */`) — never edit them by hand. They are regenerated by `npm run build:rust`. napi converts Rust `snake_case` function names to JS `camelCase` (e.g. Rust `aes128_encrypt` → JS `aes128Encrypt`).

**Data crosses the boundary as `Array<number>` (byte arrays).** Rust signatures use `Vec<u8>`; the TS side passes/receives `Array<number>`. Strings are used only where the underlying API is text-based (RSA PEM keys, password-hash strings). Convert text with `TextEncoder`/`TextDecoder` (see `tests/symmetric.test.ts`).

**The two source trees mirror each other by crypto domain.** Each domain has a Rust module under `src/` and a matching folder under `src-ts/`:

| Domain | Rust (`src/`) | TS (`src-ts/`) |
| --- | --- | --- |
| symmetric (AES) | `symmetric/aes.rs` | `symmetric/` |
| asymmetric (RSA, Ed25519) | `asymmetric/` | `asymmetric/`, `signature/` |
| hashers (SHA, BLAKE2) | `hashers/` | `hashers/` |
| password hashers (Argon2, bcrypt, scrypt) | `password_hashers/` | `password-hashers/` |
| key exchange (X25519) | `key_exchange/` | `key_exchange/` |
| message auth (HMAC) | `message/` | `message/` |
| sponges (Ascon AEAD) | `sponges/` | `sponges/` |
| hybrid (HPKE) | `hybrid/` | `hybrid/` |
| compression (zstd) | `compression/` | `compression/` |
| post-quantum (ML-KEM, ML-DSA, SLH-DSA) | `pqc/` | `pqc/` |

- Structs returned across the boundary (key pairs, encrypt/encapsulate results) are declared `#[napi(object, js_name = "<RustStructName>")]`, so they surface as plain JS objects / TS interfaces under their Rust name. Don't use `#[napi(constructor)]` for them: it generates a wrapped native class whose raw-pointer derefs CodeQL flags (`rust/access-invalid-pointer`).
- `src/lib.rs` declares every Rust module — a new module must be registered there.
- `src-ts/index.ts` is a barrel that `export *`s every domain's `index.ts` — a new wrapper must be re-exported up the chain to be part of the public API.
- Wrappers are plain classes that delegate 1:1 to the FFI function and carry the JSDoc (the FFI layer has none). Some domains add a factory + base-interface + enum to select an implementation at runtime — see `src-ts/hashers/` (`HasherFactory` / `IHasherBase` / `HasherType`) and `src-ts/password-hashers/` for the pattern to follow.

**Adding a new algorithm** typically means: (1) write the `#[napi]` function in the right `src/<domain>/*.rs` module (and register the module in `src/lib.rs` if new); (2) run `npm run build:rust` to regenerate `index.d.ts`/`index.js`; (3) add a TS wrapper class in `src-ts/<domain>/` delegating to the new camelCase function; (4) export it through the domain `index.ts` and `src-ts/index.ts`; (5) add a usage example to `docs/EXAMPLES.md`.

## Keeping `docs/EXAMPLES.md` in sync

`docs/EXAMPLES.md` (linked from the README) is the public usage reference and must cover **every public method of every exported wrapper class**. Whenever you add, rename, remove, or change the signature of a public wrapper method in `src-ts/`, update `docs/EXAMPLES.md` in the same change — don't wait to be asked:

- Add new methods to the existing section for their domain, or add a new `##` section for a new domain, plus the class to the import block at the top.
- Examples import from `"cas-typescript-sdk"`, use the `toBytes`/`toText` helpers defined at the top of the file, and only use types that are actually exported from `src-ts/index.ts` (otherwise rely on inference).
- Mirror real argument order and semantics from the wrapper (e.g. hasher `verify*` takes the hash first, then the data).
- Check coverage with: `python -c "import re,glob;d=open('docs/EXAMPLES.md').read();print([(f,m) for f in glob.glob('src-ts/**/*.ts',recursive=True) if 'class ' in open(f).read() for m in re.findall(r'^\s*(?:public\s+|static\s+)*(\w+)\s*\(',open(f).read(),re.M) if m not in ('constructor','if','return','switch') and '.'+m+'(' not in d] or 'ALL COVERED')"`

**Memory zeroization is enabled globally.** `src/lib.rs` installs `zeroizing_alloc::ZeroAlloc` as the global allocator so freed heap memory is zeroed — relevant when handling key material.

## Inline Rust tests & NIST vectors

Rust modules keep their `#[test]` functions inline in the same `.rs` file (e.g. round-trip encrypt/decrypt checks). Some TS tests validate against official NIST/FIPS known-answer vectors stored under `tests/data/` (AES GCM `.rsp`, SHA-3 `.rsp`); see `tests/aes-fips.spec.ts` and `tests/hasher.spec.ts` for how those `.rsp` files are parsed.

The `tests/wycheproof-*.spec.ts` files use [Wycheproof](https://github.com/C2SP/wycheproof) vectors that are **downloaded, not committed**: `scripts/fetch-wycheproof.mjs` (run by `npm run node:test`, or `npm run wycheproof:fetch`) pulls the files listed in its `FILES` array from the latest upstream `main` (resolved to a commit SHA and logged) into `tests/data/wycheproof/` (git-ignored), so every run tests the newest vectors; files upstream has since removed (`PINNED_FILES`) come from a fixed commit. Set `WYCHEPROOF_REF` to a SHA to reproduce a specific run. Load them with `loadWycheproof()` from `tests/helpers/wycheproof.ts`. Wycheproof `result` is three-way: assert `valid` and `invalid`, but let `acceptable` go either way.

## CI

`.github/workflows/main-pr-linux.yml`, `main-pr-macos.yml` and `main-pr-windows.yml` run `npm ci` then `npm test` on every PR, whatever its base branch (same as `cas-lib`), each across a Node.js LTS matrix (22.x, 24.x, 26.x) with `fail-fast: false`. `main-publish.yml` builds the native addon once on Node 26.13.1 (N-API binaries are not tied to a Node version) and publishes to npm. When the supported Node.js lines change, update the three PR matrices, the Node version in `main-publish.yml` (both `setup-node` steps, plus the `node-tarball` URL **and** its `node-sha256` for both Docker targets — the official `linux-x64` tarball from nodejs.org and the unofficial `linux-x64-musl` one, each hash taken from that release's `SHASUMS256.txt`) and the "Supported Node.js Versions" table in `README.md` together. Refresh the two `nodejs-rust` image digests in the same PR if the images need a newer Node or Rust (`docker buildx imagetools inspect ghcr.io/napi-rs/napi-rs/nodejs-rust:<tag>`, top-level Digest).

Every workflow sets `permissions: {}` and grants each job only what it needs, checks out with `persist-credentials: false`, and pins actions to commit SHAs with a `# vX.Y.Z` comment (Dependabot keeps those current). Dependabot doesn't touch the `docker run` image digests, the Node tarball checksums or the `npm@` version in the publish job, so those are bumped by hand.

PR titles must follow [Conventional Commits](https://www.conventionalcommits.org/) (e.g. `fix(rsa): reject keys under 2048 bits`, or `feat!: ...` for a breaking change), because PRs are squash-merged and the title becomes the commit message and changelog line. `pr-title.yml` enforces this with the same regex as `cas-lib`, so keep the two in sync.

## Releases

Releases are made with [release-please](https://github.com/googleapis/release-please) (`release-type: node`; cas-lib uses release-plz, which only publishes Rust crates), and `CHANGELOG.md` uses cas-lib's format. The `release-please` job in `main-publish.yml` runs on every push to `main`:

1. It opens or updates a `chore: release <version>` PR that bumps `package.json` / `package-lock.json` and `.release-please-manifest.json`, and adds a `CHANGELOG.md` entry built from the Conventional Commit titles since the last release. Edit that PR to polish the entry; don't edit `CHANGELOG.md` entries anywhere else.
2. Merging it makes the job push the `v<version>` tag and create a GitHub Release whose body is that entry (job outputs `release_created` / `tag_name`).
3. The `publish` job then ships that version to npm. (Until #151 gates it on `release_created`, `publish` runs on every push to `main`.)

`changelog-sections` in `release-please-config.json` maps commit types to cas-lib's groups: `feat` → Added, `changed` → Changed, `deprecated` → Deprecated, `fix` → Fixed, `security` → Security, `docs` → Documentation, everything else → Other; `!` commits are also listed under Breaking changes. release-please has no catch-all, so a type added to the `pr-title.yml` regex must be added there too or its commits are left out of the changelog. `release-as: "2.0.0"` pins the first release and must be removed once 2.0.0 is out. `Cargo.toml`'s version is not kept in step: the crate is never published, and bumping it would also need `Cargo.lock` updated for `--locked` builds.

The PR that brings an epic branch into `main` must be merged with a **merge commit**, so each sub-PR's squashed Conventional Commit reaches `main` and gets its own changelog line. If it is squashed, put a `BEGIN_COMMIT_OVERRIDE` … `END_COMMIT_OVERRIDE` block listing every sub-PR title in the squash body; otherwise release-please sees one commit. release-please reads that marker from the body of the PR each commit came from and replaces the commit message with whatever follows it, so never write the literal marker in any other PR body (it would replace that PR's changelog line), including the epic PR's when it is merged with a merge commit (it would add duplicate lines).

A release PR opened with the default `GITHUB_TOKEN` doesn't trigger the PR workflows, so the job uses the `RELEASE_PLEASE_TOKEN` secret (GitHub App or fine-grained PAT with Contents and Pull requests read/write) when it is set.
